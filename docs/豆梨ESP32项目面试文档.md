## 1. 面试前先看这一页

### 一句话定位

豆梨是面向床头陪伴、日常问答和个人资料管理的语音助手：ESP32 负责唤醒、收音和播放，本地 Node.js 服务编排语音识别、模型回答、记忆与工具，React 提供管理界面，并向安卓独立运行和局域网多端同步扩展。

### 一分钟项目介绍

> 我做了一个叫豆梨的个人语音助手，最初想解决的是睡前、休息时还要拿手机打开聊天应用的问题，希望直接唤醒床头设备就能交流，而且下次聊天能记住我确认过的偏好。
>
> 架构上，ESP32 负责本地唤醒和音频交互，电脑上的 Node.js 服务接收音频，串起 ASR、模型回答和 TTS。浏览器和设备复用同一个对话引擎，管理页面用 React，本地数据用 SQLite。
>
> 我重点处理了三个问题：语音打断后旧回答不能继续播；长期记忆要有原话来源，能确认、更正和忘记；不同问题需要结合上下文选择合适的模型。后续又加入安卓服务和手机、电脑之间的加密同步。
>
> 目前 Windows 和微雪 ESP32 的真人免按键唤醒、提问与回复已经有验证记录，当前代码的 62 项自动化测试也通过了。安卓构建和同步软件链路已有验证，手机锁屏运行和 ESP32 自动接手还在继续验收。

### 三分钟展开顺序

1. **场景**：床头免手持交流，需要自然停顿、可打断、跨会话记忆。
2. **架构**：设备音频入口、共享对话引擎、外部模型服务、本地数据与管理界面。
3. **主讲一个难点**：AI 岗优先讲记忆可信性；前端或实时交互岗优先讲语音异步状态；全栈岗可讲离线同步。
4. **结果**：真人唤醒回复记录、自动化测试和真实模型样例分别说明。
5. **下一步**：真实语音环境评测、安卓持续运行、跨设备接手，以及按测量结果优化延迟。

## 2. 项目背景与目标

### 2.1 从什么需求出发

核心使用场景是私人环境中的床头语音交流。普通聊天界面需要打开应用、输入或按住录音；持续使用时，还会重复交代名字、饮食偏好、最近的计划等背景。把模型接到硬件后，又会遇到新的问题：用户说完如何判定、回答还没播完如何插话、设备重连后如何恢复、模型说“记住了”是否真的保存。

因此，项目围绕三件事展开：

- **交流入口**：设备本地唤醒，支持语音与文字，电脑界面能够管理配置和记录。
- **持续使用**：明确偏好、已确认事实、近期经历和原始聊天分别保存，支持查询、更正与遗忘。
- **运行与控制**：模型按场景选择，工具执行有实际结果，服务可以独立常驻，并逐步让手机承担本地主机职责。

当前定位是个人使用的完整应用原型，主要约束是体验、正确性、隐私和可维护性。没有现成的商业用户规模、留存率或生产容量数据。

### 2.2 为什么采用本地服务

本地服务保存用户配置、聊天、设备配对和记忆，管理界面只对本机开放；ESP32 通过局域网访问独立设备端口。这使用户可以管理自己的资料，也方便接入局域网硬件。

“本地服务”描述的是编排和数据存储位置。ASR、对话模型、TTS、向量生成等仍调用配置的外部服务，相关输入会发送给服务商。端侧唤醒与云端回答承担不同任务，不能把整个系统描述为离线大模型。

### 2.3 可以归纳的工程工作

| 工作方向 | 具体内容 |
| --- | --- |
| 交互与应用 | React 管理界面、聊天流、浏览器录音播放、记忆核对与报告确认 |
| 服务端编排 | Fastify 接口、WebSocket 网关、共享对话引擎、模型适配、有限工具循环 |
| 数据与一致性 | SQLite、证据关联、记忆版本、派生数据失效、离线同步 |
| 设备集成 | 小智协议适配、服务发现、批准/撤销、Opus 编解码、固件资源与激活兼容排查 |
| 交付与验证 | 独立后台启动、隔离测试、真实模型检查、设备日志和真人反馈核对 |

ASR、语言模型、语音合成、Opus 和唤醒模型来自已有服务或开源组件。项目的技术重点是把这些能力组织成可使用、可解释、可恢复的应用。

```text
  OTA 服务发现 + WebSocket 控制消息和 Opus 音频
                         │
                         ▼
                 设备服务 :8789
                         │
浏览器 / Android WebView │
  React 管理与聊天       │
  文字：HTTP NDJSON      │
  语音：WebSocket PCM    │
             │           │
             ▼           ▼
  本机管理服务 :8788 → VoiceConnection / ChatEngine
                         │
         输入纠错 → 场景路由 → 记忆上下文 → 回答 / 工具
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
  模型适配层         SQLite 本地数据      工具服务
  ASR / LLM / TTS    偏好、事实、证据      历史与记忆查询
  Embedding/Rerank   摘要、聊天、配置      搜索、家居、传感器
       │                 │                 健康专用流程
       └─────────文字增量 / 分句语音────────┘

       认证广播 + 共享 .local 名称

```

安卓方案把 Node 服务放入 App 的独立进程，WebView 打开手机自身的回环管理地址。它有自己的数据库和运行时，具体实现与当前验收边界见第 8 节。

### 3.2 技术栈与选择依据

| 层次 | 当前实现 | 选择考虑 |
| --- | --- | --- |
| 管理界面 | React 19、Vite、Lucide | 以组件组织聊天、记忆、设备、设置和健康页面 |
| 本地服务 | Node.js ESM、Fastify、`ws` | 共用 JavaScript 技术栈，便于处理 HTTP、WebSocket 和异步模型调用 |
| 数据库 | Node 自带 SQLite、WAL、外键、事务 | 个人本地应用易部署，关联数据和状态迁移可在本机完成 |
| 音频 | AudioWorklet、WebAudio、PCM/WAV、`opusscript` | 浏览器采集与播放；设备链路压缩音频；服务端统一处理 |
| 模型接口 | Chat Completions、转写、合成、Embedding、Rerank 适配 | 各职责独立配置，兼容性由实际接口实现和检查确定 |
| 记忆检索 | 中文分词/BM25、向量余弦相似度、重排 | 同时覆盖精确词语和语义相近表达 |
| 多端同步 | SQLite 触发器、逻辑时钟、AES-256-GCM、HKDF | 追踪行级修改，确定合并顺序并保护传输内容 |
| 安卓 | Java Activity/Service、JNI、第三方 nodejs-mobile、WebView | 复用服务端与网页实现，处理手机原生生命周期 |

SQLite 开启 WAL 和 5 秒忙等待。它适合目前的个人数据量与部署目标；同步数据库调用和全量候选检索也意味着需要限制单次工作量，不能据此声称具备大规模并发能力。

### 3.3 “你好豆梨，给我讲讲闭包”经过哪些步骤

1. ESP32 的本地模型识别唤醒词，固件建立语音连接并上报握手与音频参数。
2. 服务端验证设备批准状态和令牌，将 Opus 解码为统一 PCM。
3. 根据能量和静音时长完成断句，将整句录音交给 ASR，得到原始文本。
4. 输入层应用已确认词典；可选模型精修需要通过数字和否定词保护。
5. 路由层结合当前问题和近期上下文，输出场景与能力档位，再由程序选择模型。
6. 记忆服务召回已确认事实与相关摘要，加上预算内的历史和当前消息。
7. 模型流式输出文字；需要时调用记忆、历史或其他已开放工具。
8. 网关把文字按句加入串行 TTS 队列，转换为 PCM / Opus 音频帧发送。
9. 保存对话结果与相关元数据，后台再处理记忆提取和摘要任务，设备恢复收听。

健康场景有独立的数据与回答流程：敏感内容进入加密健康表，普通聊天表仅留引用和占位文本。

## 4. 主讲难点一：长期记忆如何可信、可更正、可遗忘

### 4.1 一分钟主答

> 长期记忆最难的是，用户改了或删了一个事实以后，系统不能又从旧摘要、历史消息或晚返回的检索结果里把它带回来。比如用户先说住北京，后来更正为上海，日常回答要用新事实；问过去住哪里时，又要能查到当时有效的版本。
>
> 我把原始消息、结构化事实、证据和摘要分开保存。自动提取只生成建议，确认后才成为可用事实；同一人物、同一属性的更正保留旧版本和有效期。删除时同时清理相关摘要、向量，并把关联原话和可追溯的衍生回答排除出后续记忆查询。
>
> 还有一个容易漏掉的竞态：向量检索正在等待网络时，用户可能已删除记忆。所以外部请求回来后还要重读数据库，检查记录状态和版本。正确性约束放在程序和数据库里，模型负责提取和理解。

### 4.2 四类信息各自解决什么问题

| 信息 | 典型内容 | 使用方式 |
| --- | --- | --- |
| 明确偏好 | 用户在页面设置回答简短 | 优先级高于模型提取的资料 |
| 结构化事实 | 用户目前住上海、不吃香菜 | 带人物、属性、状态、有效期和证据 |
| 近期摘要 | 昨天聊到周末出行安排 | 用于恢复近期话题，保留原话关联 |
| 原始聊天 | 某天用户具体说了哪一句 | 作为证据和历史查询来源 |

**会话历史**解决当前对话连贯性，**长期记忆**解决跨会话的事实与偏好，**检索**负责从这些持久数据中找出本轮需要的部分。摘要不能自动升级为用户永久偏好。

### 4.3 数据模型

核心表包括：

- `messages`：原始消息及输入、路由等元数据。
- `memories`：`subject`、`predicate`、`object/value`、`kind`、`status`、`valid_from`、`valid_until` 等。
- `memory_evidence`：事实与消息的关联，保存逐字原话和观察时间。
- `memory_summaries`、`summary_sources`：摘要及其输入消息关系。
- `memory_vectors`：向量、内容哈希和模型标识。
- `memory_pending`：当前会话待确认的操作、源消息与过期时间。
- `memory_jobs`：持久化提取任务及重试状态。
- `memory_exclusions`、`forgotten_memories`、`forgotten_facts`：检索排除与遗忘抑制指纹。

属性必须足够具体。例如 `food:香菜` 和 `food:面条` 分别保存，两种偏好可以同时存在。用一个泛化的“饮食偏好”键会把互不冲突的事实错误覆盖。

### 4.4 从原话到已确认记忆

```text
用户原话
  → 持久化消息
  → 后台提取候选事实
  → 校验结构及逐字证据
  → suggested / conflict / needs_review
  → 用户确认
  → active
  → 到期为 expired，替换后旧版为 superseded
```

同属性新值与旧值冲突时，需要明确替换。原话被纠正后，依赖该原话的事实需要复核，固定记忆也不能跳过来源校验。多条同义事实可以合并证据；模型给出的置信度只作辅助信息。

证据校验能够确认“原话确实包含这段引文”，不能证明模型对原话的语义理解必然正确，因此保留人工确认。

### 4.5 语音确认如何避免误操作

例如用户说“记住，我不吃香菜”：

1. 从明确命令中识别记忆操作，提取事实并找到同属性旧记录。
2. 保存待确认操作，记录 `session_id`、源文本哈希、目标记录版本和 **5 分钟**有效期。
3. 向用户复述准备写入或替换的内容。
4. 当前会话收到“确认”后，重新检查源消息和目标版本，也检查是否出现了新的同属性冲突。
5. 在数据库事务中写入；多条事实中任一失败则回滚。

“确认”只能消费当前会话的待确认操作；其他话题会清掉旧确认，防止下一句“好”意外改动之前的资料。

### 4.6 混合检索具体怎样实现

当前检索在本地 SQLite 数据之上实现，没有独立向量数据库。

1. 用 `Intl.Segmenter("zh")` 分词、过滤停用词，对较长中文词补相邻双字片段。
2. 计算 BM25 词法得分，并用 `score / (score + 1)` 压缩数值范围。
3. 调用 Embedding 生成查询向量，与本地保存的有效向量计算余弦相似度。
4. 用当前实现的加权公式合并：

   ```text
   combined = 0.35 × lexical
            + 0.65 × cosine（cosine 达到阈值才计入）
   ```

5. 对排名靠前的最多 **24 条**候选进行重排，并按相关性阈值过滤。
6. 去除高度重复的候选，重新检查数据库中的有效状态、更新时间与内容，最后按上下文预算装入。

在现有硅基流动配置下，可复用 `BAAI/bge-m3` 和 `BAAI/bge-reranker-v2-m3`。它们是项目已有配置口径，具体服务是否可用由运行时检查确定。

默认向量阈值 **0.42**、重排阈值 **0.01** 是当前参数，并非跨模型通用标准；权重也属于实现中的经验选择，后续需要检索样本集评估。

**为什么两路结合？** 精确词语适合找名字和具体属性，向量有助于找到措辞不同的相关事实；重排进一步比较问题与候选的关系。语义调用失败时保留词法检索结果，并显示降级状态。

### 4.7 索引更新与上下文预算

向量记录同时绑定 `model_key` 与 `content_hash`。模型服务地址/模型名变化或文本变化时，旧向量不再参与当前匹配，后台逐批重建。生成向量期间文本又被修改，写回前检查内容哈希，避免旧向量覆盖新内容。

默认记忆预算为 **2400 个估算 token**：约 30% 给明确偏好及核心事实，40% 给相关事实，25% 给近期经历，其余留作结构余量。历史另有 **5000 个估算 token**预算，当前用户消息单独追加。

这是按字符估算的工程预算，并非模型 tokenizer 的精确计数。当前实现优先取近期完整历史项，尚不是保证完整问答对或工具组的严格裁剪算法；扩展时可增加分组保留和精确计数。

### 4.8 遗忘为什么比删除一行复杂

某条事实可能同时出现在事实表、摘要、向量、原话以及引用过它的回答中。当前遗忘流程会：

- 删除对应事实；语音遗忘按同人物、同属性覆盖历史版本。
- 清理关联摘要与向量等派生数据。
- 将关联原话及可追溯衍生回答排除出后续记忆上下文和查询。
- 保存指纹，抑制后台把同一内容再次自动提取出来。
- 在多端同步中传播删除和排除记录，清理另一端的相关派生数据。

原始聊天仍能在聊天记录中查看或另行删除。遗忘不等于删除所有原始历史；指纹和关联清理也不能保证识别所有语义改写。

### 4.9 后台任务如何恢复

提取任务保存在 SQLite，失败按递增间隔重试；每批最多处理 3 条提取、3 份摘要和 64 条向量，提取尝试达到 5 次后保留待重试状态。后台运行有单任务保护，避免定时触发和消息触发重叠执行。

摘要按会话和本地自然日组织，每一点都要有能匹配原文的证据。生成完成后再次确认输入未被改动；事务提交摘要与来源关联。这样可以处理模型等待期间发生的更正和删除。

## 5. 主讲难点二：语音打断与异步状态一致性

### 5.1 一分钟主答

> 语音交互里，一个“停止”会同时影响识别、模型生成、语音合成和已经排队的播放。最典型的问题是用户开始下一轮了，上一轮很慢的 TTS 才返回，旧回答又突然播出来。
>
> 我的处理分两层：用 AbortController 取消仍在运行的请求，同时给语音处理维护 generation。每次新一轮或打断都让旧 generation 失效，合成完成和发送音频帧之前都检查自己是否仍属于当前轮次。
>
> TTS 通过 Promise 链按句串行执行，浏览器也维护已调度的音频节点。主动打断会停止这些节点；正常告别则先释放麦克风，等告别音频播完再关闭。测试会刻意让旧请求晚返回、模型中途失败和连接替换，检查是否还能正确开始下一轮。

### 5.2 音频链路与断句

| 环节 | 当前处理 |
| --- | --- |
| 浏览器采集 | `getUserMedia` + AudioWorklet，请求单声道、回声消除、降噪和自动增益 |
| 统一音频格式 | 16 kHz、单声道、PCM16LE；ASR 请求封装 WAV |
| ESP32 传输 | Opus 编解码，兼容小智音频帧 v1/v2/v3 |
| 开始说话 | RMS 能量达到阈值，保留约 200 ms 前置音频，减少首字截断 |
| 结束说话 | 按静音时长、最大录音时长或手动提交结束 |
| 输出播放 | 重采样到 16 kHz；按 20 ms 音频帧发送，设备侧编码为 Opus |

20 ms × 16000 Hz = 320 个采样点，16 位单声道对应 **640 字节 PCM**。输入每秒为 32000 字节，所以 6400 字节前置缓冲约等于 200 ms。

RMS 是能量阈值法。轻声可能低于阈值，持续噪声可能高于阈值；浏览器请求回声消除也不代表真实设备上的回声和打断效果已经通过。

### 5.3 实时程度怎么准确描述

当前直接模型路径是：**整句 HTTP 识别 → 流式文字回答 → 按句合成播放**。

模型输出累计到一定长度和标点后，先把已完成句子送去 TTS，后续文字可以继续生成。TTS 句子按 Promise 链串行，避免后一句先合成完成导致乱序；一段句子的合成结果取得后，再按播放节奏发送音频帧。

项目另有可选自建流式 ASR 桥接。它使用请求 ID、`start/partial/final/stop` 与 PCM 分片；流式失败或等待最终结果超时后启动一次 HTTP 回退，通过 `Promise.any` 选取成功结果并清理另一条路径。这个接口需要桥接服务适配具体厂商协议。

### 5.4 为什么取消请求后还要校验轮次

取消信号不能撤回已经完成的响应，也不能自动删除已进入 Promise 队列的任务。轮次校验提供第二道约束：

```javascript
// 从现有实现提炼的逻辑，省略业务细节
const generation = ++connection.generation;
const signal = controller.signal;

const active = () =>
  !signal.aborted &&
  generation === connection.generation &&
  socket.readyState === OPEN;

const audio = await synthesize(sentence, signal);
if (!active()) return;

for (const frame of audioFrames(audio)) {
  if (!active()) return;
  send(frame);
}
```

语音连接只取消自己持有的 controller，避免旧连接关闭时误取消共享会话中的新连接。对话引擎另按会话维护活动请求，新请求进入同一会话时停止旧轮次。

### 5.5 各类结束如何处理

| 情况 | 处理 |
| --- | --- |
| 正常回答结束 | 等待语音队列完成，发送停止状态并恢复收听 |
| 主动打断 | 使旧轮次失效、取消请求、停止播放，允许新一轮输入 |
| 模型中途失败 | 取消当前及排队音频，确认仍是当前轮次后报告错误并恢复收听 |
| ASR 返回空文本 | 恢复收听，不凭空创建用户消息和回答 |
| 文字完成但 TTS 失败 | 保留文字结果，明确报告语音失败 |
| 用户告别 | 浏览器立即停止录音，排空告别播放后关闭会话 |
| 设备断线 | 清理连接、编解码器及待处理 RPC；重连可恢复该设备最近会话 |

### 5.6 如何拆解延迟

```text
停止说话到首段可听声音
≈ 断句等待 + ASR + 输入处理 + 路由 + 记忆检索
  + 模型首句生成 + 首句 TTS + 传输/播放缓冲
```

先分别测每段，尤其区分“首 token”“首句”“首个可听音频”和“完整回答结束”。代码已有 ASR、路由、首 token 和总耗时等记录；首个真实可听声音仍需要端侧测量。

分句合成减少等待整段回答的时间；问候、明确追问等跳过分类也能减少一次调用。具体优化收益需保持相同输入、模型和网络条件后测量，不能用单次接口耗时代表整体语音延迟。

## 6. 模型路由与工具调用

### 6.1 为什么分类和选择模型分开

同一个助手既要聊天，也可能讲知识、解题或讨论健康。问题短不代表简单，“这个药能不能一起吃”仍可能涉及个人决策。

分类模型只输出结构化结果：

```json
{
  "route": "learning",
  "complexity": "moderate",
  "personalDecision": false,
  "needsSearch": false,
  "continuation": true,
  "confidence": 0.95
}
```

程序校验字段与枚举，再选择配置中允许的模型。模型名称、密钥、地址和执行权限由程序管理，分类器不能自行指定任意服务。

### 6.2 一轮路由的优先关系

1. 用户手动选场景，优先按手动模式。
2. “继续讲”“举个例子”等明确追问，沿用上一轮主题和能力档位。
3. 简单问候与明确设备动作跳过模型分类。
4. 其他表达结合最近对话分类；明确换话题重新判断。
5. 分类超时、输出不合法或低把握时，按设置执行本地规则与质量优先回退。
6. 有场景专用模型先用专用模型；需要强模型且已配置时使用强模型；否则使用日常模型并记录降级。

五个场景是日常、学习、解题、健康、辨析。健康、复杂任务、个人重要决策等进入质量档。健康场景还会转入专用健康服务，因此最终回答调用要结合健康服务实际配置解释。

### 6.3 当前文档记录的模型配置

| 任务 | 现有项目文档记录 |
| --- | --- |
| 日常对话 | `Qwen/Qwen3.5-35B-A3B` |
| 路由 / 记忆整理 | `Qwen/Qwen3.5-4B` |
| 强回答模型 | `deepseek-ai/DeepSeek-V4-Pro` |
| ASR | `Qwen/Qwen3-ASR-1.7B` |
| TTS | `FunAudioLLM/CosyVoice2-0.5B` |
| 向量 / 重排 | `BAAI/bge-m3` / `BAAI/bge-reranker-v2-m3` |

这些是截至整理日期的项目配置记录，可在设置中替换。本次没有读取或导出用户密钥；面试重点是模型职责、选择机制和实际验证条件。

### 6.4 如何观察路由是否正确

每轮记录场景、能力档位、分类来源、分类状态、选择原因、分类耗时、模型配置及实际返回的模型名。未配置强模型和分类超时也显示出来。

`confidence` 表示分类器自报的分类把握，不能作为答案正确率。现有 12 个真实分类样例通过，只能支持这些样例的结论；评估整体效果需覆盖追问、换话题、短问题、长闲聊和失败回退。

### 6.5 工具如何约束执行

对话引擎有最多 4 次模型调用的工具循环，支持记忆、历史、可选搜索、已配置家居动作和传感器查询。工具仅在具备对应配置时开放，结果以结构化事件交给界面，并回传模型继续回答。

家居动作还检查用户文本是否具有明确操作意图；提问、否定和假设表达不直接执行。可用动作 ID 来自配置白名单。同一轮使用 `Map<actionId, result>` 复用同一动作首次结果，降低模型重复调用造成的重复按压。

这个去重范围是单轮、进程内，不能承诺跨轮次或外部设备的 exactly-once。HTTP 接收成功与实体状态已改变也要区分；Home Assistant 可额外读状态核验，没有反馈能力的设备只能报告指令接收结果。

## 7. 前端与交互实现

### 7.1 文字流如何送到界面

文字聊天接口 `/api/chat` 返回 `application/x-ndjson`，每行一个 JSON 事件。前端用 `fetch` 的 ReadableStream 读取，`TextDecoder` 增量解码，缓存不足一行的数据，再逐行解析。

网络 chunk 不对应业务消息边界，也可能拆开 UTF-8 字符，所以不能直接对每个 chunk 做 `JSON.parse`。浏览器这条链路使用 NDJSON；模型服务内部的流格式由适配层单独解析。

典型事件包括 `session`、`user`、`route`、`delta`、`tool`、`done`、`error`、`aborted`。展示状态放 React state；流累计文本、当前会话引用、AbortController 和语音实例放 ref。最终消息按消息 ID 合并，避免完成事件造成重复显示。

### 7.2 录音和播放生命周期

- 用户点击后创建并恢复 AudioContext，再申请麦克风权限，处理播放解锁失败和权限拒绝。
- AudioWorklet 采集音频，WebSocket 传输；当前设置 `bufferedAmount` 门限，积压超过 128000 字节时不再发送该次采集帧。
- WebAudio 按 `nextPlay` 调度 PCM 音频，维护活动 AudioBufferSourceNode 集合。
- 打断时停止活动节点并清空调度时间；告别时先关闭采集，再等待播放排空。
- 页面卸载时取消文字请求、停止录音、关闭连接和 AudioContext。
- 安卓界面进入后台会发出事件，页面结束手机麦克风会话；服务进程另行维护 ESP32 服务。

发送门限能限制积压，但过载时可能丢音频，属于简单保护。长时间网络抖动下的质量仍需单独评估。

### 7.3 UI 如何表达真实状态

记忆区分建议、冲突、已确认和待复核；健康报告区分已上传、已识别和已核对；模型区分期望档位、实际模型与回退原因；动作区分接收与状态核实。

这些状态由接口和持久数据决定，避免仅凭模型输出一句“记住了”或“已经打开”就显示成功。

健康表单提交携带 `revision`。读取后若被本机其他操作或同步更新，旧版本提交返回冲突，要求刷新，避免覆盖用户刚刚完成的修改。

### 7.4 前端追问：还有哪些需要加强

当前文字流逐次更新 React state；输出密集时可以按时间片合并渲染，再观察滚动和输入响应。切换历史会话时，现有逻辑会先停止流和语音，但会话详情请求还可增加请求序号校验，完整处理快速切换下的旧查询晚返回。

这两项属于进一步改进方向，不描述为已经完成的性能优化或全面竞态防护。

## 8. 安卓运行、多端同步与自动选择主机

### 8.1 安卓为什么能承担主机职责

APK 包含网页构建结果、服务源码、生产依赖和第三方 Node 移动运行库。Java 前台服务通过 JNI 启动 Node；服务在 `:engine` 独立进程中运行，管理接口监听 `127.0.0.1:8788`，设备接口使用 8789。

WebView 加载手机本地页面，原生部分负责服务生命周期、权限、通知、网络状态和诊断。界面不必一直开着才能在设计上保留设备服务，但系统与厂商省电策略是否允许持续运行必须实机验证。

目前使用第三方维护的 nodejs-mobile 预发布移动构建。构建成功和 Windows 上运行移动入口的检查不能替代 ARM 手机运行与锁屏验收。

### 8.2 同步哪些内容

同步持久用户数据：聊天、记忆与证据、遗忘记录、偏好、词典、模型和语音配置、健康档案及原件、ESP32 授权。

运行日志、音频、任务队列、向量索引与在线状态留在本机。派生数据可以重建，也往往与本机模型、运行状态有关，避免把整个数据库文件直接互相覆盖。

### 8.3 行级同步如何捕获修改

SQLite 触发器监听相关表的插入、更新和删除，每次本地写入增加逻辑时钟，在 `sync_rows` 保存：

```text
collection + primary key + clock + author(device id) + deleted
```

同步先交换元数据清单，拉取需要的行，应用后重新读取本地清单并推送对端缺少的变化。健康原件逐份传输，以约束单次数据量。应用远端记录时用 `applying` 标志避免把远端写入当成本地新修改再次递增。

### 8.4 同一条记录离线同时修改怎么办

当前采用确定性行级合并：

1. 一方是删除、一方是普通版本时，删除胜出。
2. 删除标志相同，逻辑时钟更大的版本胜出。
3. 时钟相同，按设备 ID 排序决定。

双方使用同一比较规则，获得相同的一组变更后会选到相同结果。逻辑时钟反映已观察到的修改顺序，不是现实世界时间；设备 ID 只用于打破平局。

当前没有逐字段合并和同一记录冲突版本保留。比如手机改用药说明、电脑同时改同一档案另一字段，最终可能丢掉其中一端的修改。产品化可增加冲突展示或更细粒度记录，但这是扩展方案。

### 8.5 为什么删除要有墓碑

只删除本机记录，离线设备再次上线时可能把旧副本传回来。墓碑保留“这个 ID 已删除”的信息，比较规则让删除优先，且删除的 ID 不复用。

父记录删除还要处理子记录。例如会话删除后，另一端迟到的消息不能把会话和消息重新恢复出来。实现使用事务、外键检查及对子记录的墓碑补齐；插入先处理父记录，删除先处理子记录。

远端遗忘还会清理本机摘要、待提取任务和相关确认，避免只同步事实删除，却留下能重新生成事实的材料。

### 8.6 加密与配对

配对使用 10 分钟有效的一次性信息。同步数据以 AES-256-GCM 保护，HKDF 为配对请求、配对响应和数据交换派生不同用途的密钥，并以用途作为附加认证数据。

请求携带发送方、时间和唯一请求 ID，服务端检查时间窗口和重复请求；客户端校验响应的请求 ID 与对端身份。当前重复请求缓存位于内存，不能把它描述为跨进程重启仍保留的防重放日志。

各设备使用自己的本地密钥。需要同步的加密字段在本机内存中解密，放入整体加密的传输载荷，接收端再用自己的密钥加密落地，无需共用数据库本地加密密钥。

### 8.7 ESP32 怎样找到可用主机

配对后共享一个 `douli-xxxxxxxx.local` 名称。电脑和手机通过带认证的 UDP 广播声明可用性，当前优先主机响应 mDNS：电脑优先级 20，手机 10，失去广播约 9 秒后重新选择；尚未完成首次同步的主机不参与接手。

已健康连接的 WebSocket 继续使用原主机；断线后的新连接重新解析共享名称。这里只选择新连接入口，不迁移正在生成的回答、TTS 队列或内存中的连接。

网络分区时各端可能有不同视图，因此这套局域网可用性选择不提供强一致单主保证。实际切换还依赖路由器组播、防火墙、固件 `.local` 支持和重连时重新解析。

### 8.8 一分钟同步难点回答

> 手机和电脑各自保存一份资料后，最重要的是两边都能修改，而且重新连接时结果可解释。我通过数据库触发器记录每一行的逻辑时钟和设备 ID，双方交换变更清单后用同一规则选版本。
>
> 删除需要特别处理：保留墓碑，让删除优先于离线旧副本，父记录删除也要阻止子记录复活。远端修改到达后还会递增本地健康记录的编辑版本，让已经打开的旧表单提交失败。
>
> 当前取舍是行级收敛，同一行并发修改不会逐字段合并。同步和主机发现已有软件验证，但手机锁屏、路由器和 ESP32 自动接手仍需要真实设备验收。

## 9. 健康档案：来源、模型草稿与确认状态

这一模块适合回答“AI 如何处理结构化个人资料”，重点是数据与流程设计。

### 9.1 报告处理流程

```text
上传原件 → 本地保存 → 用户触发发送给模型
        → 图片/PDF 页面识别 → 结构化草稿
        → 对照原件核对 → 确认
        → 进入问答和趋势
```

支持 JPG、PNG、WebP、PDF，单文件最多 10 MB、PDF 最多 12 页。PDF.js 在前端转换页面，模型提取日期、项目、数值、单位和参考区间。未确认报告不能进入正式问答和趋势。

趋势按项目、单位和标本分组，保留原始参考范围，不自动换算单位，也不把“<2”或“阴性”强制转换成普通数值。

### 9.2 隐私与数据隔离

个人健康档案、原件、识别结果、医学对话与证据缓存保存在独立表中，用本地密钥 AES-256-GCM 加密。普通聊天表仅保存引用和占位文本，普通记忆提取不处理这些健康对话。

报告识别和健康回答仍需要发送相应内容给用户配置的模型。外部资料检索尽量使用一般主题、检查名称和明确药品名称；自由文本身份信息过滤存在覆盖限制。

### 9.3 资料和引用怎样核验

已有 MedlinePlus、PubMed、DailyMed 接口，以及可选 Brave 中文站点检索和用户授权资料导入。来源携带获取时间、地区与覆盖信息；缓存有效期为 24 小时，版本化导入资料保留发布、复核及停用状态。

模型输出引用时必须给出本次来源 ID 和原文短摘录，程序核对是否匹配本轮检索结果，剔除无效引用并显示提示。

原文匹配只证明引文有来源，不自动证明推导正确或适合当前个体。这个模块用于资料整理、解释和问题准备；其验收结果按具体测试样例说明。

### 9.4 一个前端工程细节

PDF 页面转换曾受后台标签页的动画帧调度影响。现有实现采用打印渲染模式并设置解析时限，同时补齐中文字符映射、标准字体等资源。交付记录中，一份明确虚构的中文 PDF 在约 9 秒完成识别，字段与样例相符，界面仍保留待核对状态。

该结果只说明这个样例链路通过，不能扩展成所有医院报告和扫描件的识别准确率。

## 10. 设备集成、部署与一次具体排障

### 10.1 设备接入与管理边界

管理服务仅监听回环地址并校验请求来源；设备服务独立开放到局域网。首次接入需要配对窗口、核对配对码和人工批准；WebSocket 使用设备令牌，支持撤销。

`/xiaozhi/ota/` 在本项目中提供服务发现、激活状态及连接参数。固件更新依赖另外的刷写流程，项目没有实现固件镜像分发平台。

每台设备保存独立的模式、音量和收音阈值，重连后读取配置并恢复最近会话。服务端音量是输出 PCM 增益，夜间再叠加夜间音量，不能解释为修改了硬件功放参数。

### 10.2 具体排障案例：唤醒资源与激活异常

已有交付记录显示，两类问题分别处理：

**唤醒资源问题。** 读回 Flash 后发现 assets 分区起始内容异常，资源索引和模型无法加载。先备份完整 16 MB Flash，再写入对应板型的官方小智 2.5.2 应用和重建资源，保留配网配置。资源包含 MultiNet7 中文模型与所需 FST 文件，串口确认加载“你好豆梨”，随后用户确认免按键唤醒和回复。

**激活后的异常。** 单独升级固件后仍复现过激活崩溃，因此继续核对固件的 HTTP 响应处理。发现激活流程只需状态码后，服务端改成 200/202、零长度正文并关闭连接。随后连续 4 次重新激活均进入待机，没有观察到 panic 或软件重启。

面试可强调：依据分区内容、协议处理和实际日志逐步缩小问题。4 次复测支持这次兼容修复的结果，尚不能证明全部网络竞态和长期稳定性已经解决。

### 10.3 如何独立运行与保管数据

Windows 启动器用 detached 子进程、隐藏窗口和文件日志，使服务在启动终端退出后继续运行；停止前校验 PID 对应的命令路径。该机制不等于开机自启。

模型密钥、动作令牌和健康数据按相应存储规则加密，管理界面不返回完整密钥。普通聊天及一般记忆没有统一整库加密；`local.key` 与数据位于本机，能同时读取二者的人仍可解密受保护字段。

录音默认不落盘，`.data`、`.runtime`、Flash 备份及配对凭据不进入 Git。第三方固件、协议和依赖的来源与许可单独保留。

## 12. 常见面试追问与参考短答

### 12.1 这和给大模型接一个语音 API 有什么区别？

> API 调用只解决识别和生成。连续交流还需要处理语音状态、打断、旧请求晚返回、设备重连，以及用户资料的确认和更新。我做的系统把这些状态落到连接、轮次和数据库里，并让不同入口共用对话引擎。比如用户删除记忆后，要同步清理摘要、向量和可追溯历史，避免后续又被带回模型上下文。

### 12.2 算不算 Agent？

> 它有一个范围有限的工具调用循环：模型可以查询记忆、历史、搜索或执行已配置动作，再根据结果组织回答。路由、权限、记忆确认和设备状态由程序控制。我会把它描述为带工具能力的语音助手，按实际能力解释，而不会声称它有完整的自主规划和任意任务执行能力。

### 12.3 为什么用 SQLite？

> 当前服务面向个人本地使用，SQLite 不需要单独部署数据库，便于在电脑和手机保存资料；事务和外键可以维护事实、证据和同步写入的一致性。代价是同步查询会占用 Node 线程，检索也是面向当前小数据量实现的。我通过后台分批降低单次工作量，数据和并发增长后再引入索引、工作线程或独立存储。

### 12.4 为什么不把聊天历史全放进 Prompt？

> 历史越来越长会增加成本与延迟，也容易把过期、已更正或无关内容带进回答。我保留原始聊天供查询，但日常上下文由明确偏好、相关已确认事实、近期摘要和有限历史组成。问过去具体说过什么时再通过历史工具查原话，查不到就说明没找到。

### 12.5 “我现在住上海”为什么不直接覆盖北京？

> 日常问题应该使用现在有效的上海，但用户问去年住哪时，旧事实仍可能有价值，所以更正保留历史版本和有效期。如果用户要求忘记这个属性，则需要处理所有相关版本。更正和遗忘的业务语义不同，数据库操作也不同。

### 12.6 怎样避免模型误把聊天内容记成事实？

> 提取阶段只接受结构化候选和可核对的原话证据，普通自动提取进入待确认状态。只有确认且在有效期内的事实才进入常规上下文；提问、假设和模型自己编出的内容不应直接成为用户事实。证据匹配保证引文存在，人工确认补充对含义的核对，真实误提取率还需要样本评估。

### 12.7 用户改动发生在模型请求过程中怎么办？

> 请求开始时读取的数据只是一个快照。向量检索、摘要生成或记忆提取回来以后，我会重新检查原话、内容哈希或更新时间；已经变更就不能把旧结果提交。记忆确认也携带目标版本，健康编辑带 revision，分别防止不同链路里的旧操作覆盖新状态。

### 12.8 为什么不能只调用 AbortController？

> 请求可能已经完成，也可能有回调和播放节点已经排队，所以取消网络请求还不够。服务端通过 generation 拒绝旧轮次结果，前端停止已经调度的音频节点。这样同时处理未完成工作和已返回但还没播放的工作。

### 12.9 模型路由会不会反而更慢？

> 会，分类本身增加一次模型请求，所以不能每句话都无条件分类。明确问候、简单动作和连续追问有直接路径，其他问题才结合上下文判断，分类还有超时。是否值得使用要比较整条链路的延迟、成本与答案质量，尤其关注错误降档的代价。

### 12.10 为什么文本流和音频都不统一成 WebSocket？

> 文字发送天然是一条请求对应一条响应，fetch 加 NDJSON 就能实现增量结果和取消；语音需要持续上传音频、下发音频与控制消息，更适合双向 WebSocket。两种传输最终都调用同一 ChatEngine，业务逻辑和路由不需要各写一套。

### 12.11 手机关闭或电脑休眠会怎样？

> 当前有连接的主机停止后，原语音连接会断开。设计上另一台已完成同步并可用的主机通过共享名称接收后续新连接，但这依赖手机后台存活、局域网发现和固件重连行为。双方都不可用时就无法提供服务，当前没有互联网中继或运行中任务迁移。

### 12.12 同步能保证完全没有冲突吗？

> 能保证的是在相同变更集合下按确定性规则选择行版本。同一行离线同时编辑仍可能丢失一个版本，所以我明确保留这个限制；删除墓碑防旧数据复活，revision 防旧表单覆盖新数据。若要保留双方修改，需要进一步做冲突历史、用户选择或字段级合并。

### 12.13 项目里最能体现工程判断的一点是什么？

> 我把模型输出和系统事实分开：提取结果需要确认才成为记忆，报告识别需要核对才进入问答，工具返回成功也要区分指令接收与实体状态核实。这样每个环节都有明确的数据状态和失败处理，用户能知道系统真正完成了什么。

### 12.14 AI 辅助开发时，你的价值在哪里？

> 我的责任是定义场景、状态和验收条件，并检查实现是否满足它们。比如“忘记”要求清理哪些数据，“打断”是否停止所有旧音频，“同步”如何处理删除和旧表单，都需要明确的工程决策。我用可复现的异步时序、数据库检查和真机反馈验证这些决定，AI 可以协助调查和实现，但不能代替验收结论。

### 12.15 目前最大的不足是什么？

> 软件机制已经比较完整，但长期真实使用的覆盖还不足。噪声、回声、轻声和安卓后台存活都受环境影响；记忆检索参数也需要更多真实问题校准。下一步会先固定环境和输入，记录每段延迟及失败原因，再决定优化音频、模型调用还是检索，避免只凭感觉调参数。

## 13. 连续追问练习

每次只回答当前一问，保持同一组对象和前提。

- **记忆线**：为什么需要记忆 → 原话怎样变成事实 → 什么情况下确认 → 同属性冲突 → 查询过去版本 → 遗忘如何清理 → 检索过程中删除 → 如何测试。
- **语音线**：音频怎样采集 → 为什么 16 kHz/20 ms → 如何断句 → 怎样先播第一句 → 为什么串行 TTS → 为什么取消还要 generation → 告别和打断区别 → 真实延迟怎么测。
- **路由线**：为什么多个模型 → 分类输入输出 → 追问怎样继承 → 低把握怎样回退 → 如何知道实际调用哪个模型 → 分类耗时是否值得。
- **同步线**：为什么不复制数据库 → 如何记录变更 → 并发谁赢 → 为什么不用现实时间 → 删除为何留墓碑 → 旧表单怎么办 → 为什么自动发现不等于无缝接手。
- **前端线**：NDJSON 怎样解析 → chunk 为什么不能直接 JSON.parse → state/ref 分工 → 麦克风和播放何时释放 → 报告为什么先是草稿 → 冲突如何提示 → 哪些竞态仍待完善。
