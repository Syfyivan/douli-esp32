# 双人讨论与独立评理模式调研

2026-11-12 · 集成方案，待实现

建议用两句口令区分用户意图。「豆梨，我们一起聊」邀请它加入当前讨论；「豆梨，帮我们评评理」开启一次独立评理。两人讨论露营时，豆梨可以根据 A 提的周六和 B 提的天气一起出主意。进入评理时，让双方各自确认要交给评理服务的说法。结束后回到原来的对话。

## 豆梨承担的工作

- **日常讨论。** 当前共享音箱按成员分别选取个人会话。拟新增仅限本次讨论的临时上下文。两人开始讨论后，豆梨听取轮流发言，听到「豆梨，你怎么看」再开口。任一人说「结束讨论」就退出。多人机器人实验把识别说话人与判断发言对象列为两个独立问题；用点名邀请接话能先绕开对眼神和说话方向的依赖。[多人机器人研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC13124475/) · [现有声纹与会话实现](VOICE_IDENTITY.md)
- **评理。** 新开一个案件。A、B 各讲一遍，豆梨简短复述，允许纠正。两人都确认陈述和提交对象后，后台仅发送案件编号、临时代号和确认文本。遇到重叠或身份不明，请两人分开再说，或在管理页确认归属。单人聊天、历史记忆、原始音频及声纹样本都留在案件输入之外。
- **如何下判断。** 先讲双方确认的事实，再对照两人认可的约定，对具体行为给结论。比如双方都确认约好七点且未同意改期，可以指出迟到的一方没有履约；「六点半发过消息」若还只是单方陈述，就问另一方看到后怎么答复。口味偏好不同则给可选安排。允许双方更正事实后重评，任何一方都能叫停。有威胁或人身危险时停止共同评理，优先让当事人安全退出。

在 2,405 名参与者的三项预注册实验中，迎合提问者的 AI 会增强其自认有理的信念、降低其修复冲突的意愿。另一项关于公共议题讨论的研究让参与者批评并修订 AI 汇总，能将异议纳入共同表述。这为「双方复述确认、允许修正」提供了依据，情侣当面争执的效果仍需单独测试。[人际冲突实验](https://doi.org/10.1126/science.aec8352) · [共同表述研究](https://deepmind.google/research/publications/65220/)

## 自托管原型的接法

ESP32 复用已有收音、唤醒和播报。豆梨后台在分发到个人会话前处理已开启的讨论或评理，将确认的文字交给独立服务。上游使用 `POST /message`，支持 `channel_id`、`user_id`、`name`、`text`、`mentioned`，返回 `replies`。每案使用新编号，双方使用稳定的 A/B 代号。上游允许服务自行选择接话时机，豆梨应在发给扬声器之前控制播报，只朗读适合现场公开的结果。[上游 HTTP 实现](https://github.com/zdkelemen/mediator-agent/blob/1c079566392537607174c29b5fc4f088d6754a6c/mediator/adapters/webhook_app.py)

用模拟模型和虚构陈述运行了上游的命令与会话代码。A 单独陈述时可保持安静；B 接着陈述后，模型请求同时包含两人的话。只听完 A 时调用 `decide` 也会触发模型生成。上游会将会话写入 JSON，重置后文件里的消息列表变空。因此原型应在豆梨端控制提交时机，调整上游临时存储，并显式配置本地监听与鉴权。自托管服务调用云模型时，确认界面仍须说明实际接收文本的模型服务。[命令实现](https://github.com/zdkelemen/mediator-agent/blob/1c079566392537607174c29b5fc4f088d6754a6c/mediator/commands.py) · [会话存储](https://github.com/zdkelemen/mediator-agent/blob/1c079566392537607174c29b5fc4f088d6754a6c/mediator/session.py)

## 分轮验收

1. 先验证日常讨论。让 A 提地点、B 提时间，豆梨在被点名前保持安静，被问到时能同时复述两项条件，退出后个人记忆无新增。
2. 再接独立评理服务，用虚构的「约好七点」案例走通双方确认、提交、听结果和退出。交换 A/B 标签与发言顺序，核对事实和结论是否一致；再让一方补充「我同意改到七点半」，检查结论是否随证据改变。单方要求直接判、对方中途退出、服务超时都应有明确结果。
3. 最后用真实 ESP32 测中文转写、插话、错归属、无邀请播报次数和等待时长。当前验收只覆盖上游核心协议的离线行为；第三方 HTTP 联调、真实模型判断和双人真机体验均待验证。
